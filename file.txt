Astrid ISP Billing System - Milestone Reference
=============================================

This file is a working reference for the milestones we have completed, what each milestone covered, and what remains to be built.

CURRENT WORKFLOW - READ THIS BEFORE TROUBLESHOOTING

1. Astrid stores the subscriber, package, status, and encrypted service
   credentials in Convex. A PPPoE subscriber is not supposed to be copied into
   RouterOS /ppp secret. RouterOS asks FreeRADIUS to authenticate each new PPPoE
   login; FreeRADIUS calls Astrid's Convex RADIUS endpoint to check the
   subscriber. Accounting requests then update the Astrid session and RADIUS
   logs.
2. API-SSL is the management channel from the Ubuntu gateway to RouterOS. It is
   not the subscriber authentication path. The gateway configures RouterOS's
   RADIUS client and can remove a live PPPoE session when Astrid queues a
   disconnect operation.
3. Rejecting a new login and stopping an existing session are separate. A
   suspend or expiry makes a later RADIUS login fail. RouterOS does not
   necessarily re-check RADIUS for a session that is already connected, so the
   Ubuntu gateway must be running the current worker and have the correct local
   API credentials and trusted CA to remove that session. The resulting stop
   accounting event should be recorded by FreeRADIUS; the gateway also records
   completion of its disconnect operation.
4. "Queued" is not "completed". Check the gateway operation result and Ubuntu
   service log before assuming RouterOS changed. If a session remains online,
   verify the worker version, operation status, router API credentials, CA
   trust, and that the stored RADIUS session ID matches the active RouterOS
   session. Do not create a local PPP secret as a workaround.
5. Subscriber deletion is intentionally blocked when billing history (such as
   an invoice, payment, or support ticket) references the subscriber. Suspend
   the subscriber to stop service while retaining that history.
